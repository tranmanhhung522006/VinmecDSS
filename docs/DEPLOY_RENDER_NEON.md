# Deploy VinmecDSS publicly · Neon + Render

This guide uses the repository `tranmanhhung522006/VinmecDSS`. Use a **separate Neon project** and **separate Render web service** from other student projects. The app presents **synthetic** hospital operations data only.

## 1. Create a Neon PostgreSQL project

1. Log in to https://console.neon.tech/ and choose **New Project**. Suggested name: `vinmec-dss`.
2. Choose a region geographically near your Render service, Ohio (AWS US East 2), matching the Neon project shown in the setup screenshots.
3. In Neon Dashboard > **Connect**, copy the **pooled connection string** (hostname contains `-pooler`) as `DATABASE_URL`.
4. Disable connection pooling in the connection dialog and copy the **direct connection string** as `DIRECT_URL`.
5. Ensure both strings include the SSL query parameter supplied by Neon (e.g., `sslmode=require`). **Never share or commit these strings**.

The Prisma schema explicitly uses `url = env("DATABASE_URL")` and `directUrl = env("DIRECT_URL")`.

## 2. Connect GitHub to Render and deploy the Blueprint

1. Log in to https://dashboard.render.com/ and connect your GitHub account.
2. Select **New > Blueprint**, choose the repository `VinmecDSS`, branch `main`, and allow Render to read `render.yaml`.
3. The Blueprint creates one **Node Web Service** (`vinmec-dss`). All resources reside on Render except the database on Neon.
4. Enter the environment variables marked `sync: false` during Blueprint creation:

| Variable | Value / guidance |
|---|---|
| `DATABASE_URL` | Neon **pooled** connection URL; sensitive |
| `DIRECT_URL` | Neon **direct** connection URL; sensitive |
| `DEMO_PASSWORD` | Unique password (at least 16 characters) for private staff logins; never publicize |
| `OPENAI_API_KEY` | Optional; leave unset until AI testing is required |

Other environment variables are set in `render.yaml`: `JWT_SECRET` is generated by Render, `NODE_ENV=production`, `OPENAI_MODEL=gpt-4.1-mini` and `AI_MAX_CALLS=20`.

5. Confirm **Deploy Blueprint**. The build runs `npm install --include=dev && npm run db:generate && npm run build` (required because `NODE_ENV=production` would otherwise omit TypeScript development dependencies). For a manually created Render Web Service, edit **Settings > Build & Deploy > Build Command** to use this exact command; `render.yaml` changes do not automatically override manually entered commands.
6. At startup, `npm run db:push` initializes or updates the Neon schema without wiping existing data (Prisma may refuse potentially destructive schema changes). `npm run db:seed` then adds or updates demonstration aggregates and, when `DEMO_PASSWORD` is configured, protected demo accounts.
7. Render starts the same-origin app. The health endpoint is `https://<your-render-domain>/api/health` and the UI is at `https://<your-render-domain>/`.

**Security reminder:** The UI intentionally does not prefill credentials. Public visitors need no account. Manager credentials are needed only to persist scenarios or approve decisions.

## 3. Check the live site

- Visit `/`: dashboard must render without login. It should show the *synthetic dataset* disclaimer.
- Visit `/api/health`: response should report `status: ok` after connecting to Neon.
- In **What-if analysis**, set baseline 200, growth +30%; expect 260 visits and 240/270/300 capacity for 8/9/10 doctors.
- Refresh the page: public scenarios should **not** become saved records.
- Use **Staff sign in** and a privately configured manager password to verify persisted decisions.
- Avoid enabling OpenAI until DSS calculations work; if enabled, review usage and spending on the OpenAI developer platform.

## 4. Free-tier considerations

Render Free web services can sleep after idle time, causing a slow initial load. Neon Free compute can also suspend while idle. Plan to open the site before an in-class demonstration. Free tier quotas and terms may change.

## 5. Recommended next hardening

The current build is for academic demonstration, not patient data. For a real service add verified users, MFA, durable/distributed rate limiting, managed migrations, audit retention policies, monitoring, automated backups, tighter role separation, and data protection reviews.

**Never paste `DATABASE_URL`, `DIRECT_URL`, `JWT_SECRET`, or `OPENAI_API_KEY` into chat or GitHub issues.** Configure them only in Neon and Render settings.
