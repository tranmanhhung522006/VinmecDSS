# Technical outline and limitations

## Components

**Frontend** React (served from the same Render Web Service) → **NestJS API + deterministic DSS engine** → **Neon PostgreSQL**.

The optional **OpenAI Responses API** is called *from NestJS only* after numeric scenario evaluation. Results are advisory and do not modify decision data.

## Entities

`User`, `Department`, `VisitAggregate`, `ForecastRun`, `Scenario`, `Decision`, `Insight`. Historical records are aggregated per date and time slot; no patient profile is stored.

## Operational constraints

- `availableDoctors` and `rooms` are upper bounds, not weighted penalties.
- The MVP generates 3 candidate staffing configurations: current, +1 doctor, +2 doctors.
- Recommend an eligible configuration covering demand if available. Otherwise clearly show remaining shortage.
- Ranking score is a **teaching heuristic**, not a clinically validated optimization method.
- Decisions are single-finalization and actor-attributed.
- API key must remain server-side. Absence of key must not break core DSS functionality.

## Known prototype limitations

1. The forecasting baseline is simple, does not calculate MAE/MAPE on holdout data, and does not model waiting times. Future versions should back-test and validate model fit before using forecast confidence claims.
2. No shift-level staffing or multi-department optimization yet. Daily doctor productivity is an input assumption.
3. No external hospital integrations. Dashboard uses synthetic aggregates generated by seed.
4. JWT auth and RBAC protect staff operations; public visitors only access non-persistent, no-AI simulation endpoints. These controls are designed for an academic demo. Not production-ready for patient data or BYOD. Implement MFA, enterprise identity, audit hardening, rate limiting and security review before any real use.
5. The AI layer may produce ungrounded prose; human verification is mandatory. Automatic fact validation of generated sentences is not currently implemented.
6. Early-stage deployment initializes the database with `prisma db push` at service startup, an expedient approach for an academic prototype rather than a reviewed production migration strategy.
7. Neither the 14-week schedule nor proposed budget represents a real Vinmec procurement or implementation agreement.
